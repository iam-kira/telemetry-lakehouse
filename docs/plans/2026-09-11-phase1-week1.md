### Task 1: Image vs container — the single most important distinction

**Concept.** An *image* is a read-only template (like a class). A *container* is a running or stopped instance of it (like an object). One image → many containers. Deleting a container never touches the image.

- [x] **Step 1: Run an interactive Ubuntu container**

```bash
docker run -it --name box1 ubuntu:24.04 bash
```

You're now inside the container. Prove it — the hostname is a random hex string:

```bash
hostname
```

Make a file, then leave:

```bash
echo "I was here" > /tmp/note.txt
```

```bash
exit
```

- [x] **Step 2: The container still exists, stopped**

```bash
docker ps -a --filter name=box1
```

Expected: one row, STATUS `Exited (0) ...`. It's stopped, not gone.

- [x] **Step 3: Start it again — your file is still there**

```bash
docker start -ai box1
```

```bash
cat /tmp/note.txt
```

Expected: `I was here`. The container's writable layer persisted while the container existed. Now exit again:

```bash
exit
```

- [x] **Step 4: Delete the container — the file dies with it**

```bash
docker rm box1
```

**Checkpoint:** `docker ps -a --filter name=box1` returns only the header, no row. The file `/tmp/note.txt` is gone forever, because it lived in the container's writable layer. *This is why we need volumes (Task 3).*

### Task 2: Layers and the build cache

**Concept.** An image is a stack of read-only layers, one per build instruction. Docker caches each layer; if an instruction and everything above it are unchanged, the cached layer is reused. Order your Dockerfile so the stuff that changes most goes last, or you throw the cache away on every build.

- [x] **Step 1: Write a tiny Dockerfile**

Create `experiments/week1/Dockerfile`:

```dockerfile
FROM python:3.12-slim
RUN echo "layer A: rarely changes" > /a.txt
RUN echo "layer B: rarely changes" > /b.txt
COPY app.txt /app.txt
```

And `experiments/week1/app.txt`:

```
version 1
```

- [x] **Step 2: Build it and watch the layers get created**

```bash
docker build -t layerdemo experiments/week1
```

Expected: steps run, none say `CACHED` on this first build.

- [x] **Step 3: Change ONLY app.txt, rebuild, watch the cache**

Edit `experiments/week1/app.txt` to `version 2`, then:

```bash
docker build -t layerdemo experiments/week1
```

Expected: the two `RUN` steps now say `CACHED`; only the `COPY` re-runs. That's the cache working — the layers above the change were reused.

- [x] **Step 4: See the layers**

```bash
docker history layerdemo
```

**Checkpoint:** `docker history` lists your two `RUN` layers and the `COPY` layer with sizes. You can explain why editing `app.txt` didn't rebuild the `RUN` layers, but editing the Dockerfile's first `RUN` would rebuild everything below it.

### Task 3: Volumes — data that outlives the container

**Concept.** Container writable layers die with the container (you proved it in Task 1). A *named volume* is storage Docker manages outside any container; you mount it into a path. Delete the container, keep the volume, keep the data. This is exactly how Kafka, Postgres, and MinIO will hold their data all phase.

- [x] **Step 1: Create a named volume**

```bash
docker volume create mydata
```

- [x] **Step 2: Write into the volume from one container, then delete that container**

```bash
docker run --rm -v mydata:/data alpine:3.20 sh -c "echo 'survives' > /data/proof.txt"
```

(`--rm` deletes the container the instant it exits. The volume is untouched.)

- [x] **Step 3: Read it back from a brand-new container**

```bash
docker run --rm -v mydata:/data alpine:3.20 cat /data/proof.txt
```

**Checkpoint:** Step 3 prints `survives`, even though the container that wrote it is long gone. Contrast with Task 1, where the file died with the container. Clean up: `docker volume rm mydata`.

### Task 4: Networks and container DNS

**Concept.** On a *user-defined bridge network*, Docker runs an internal DNS so containers reach each other by container name. On the default bridge they can't — only by IP. Every Compose file you write gets its own network, which is why in phase 1 the bridge can dial `kafka:9092` by name.

- [x] **Step 1: Create a network**

```bash
docker network create labnet
```

- [x] **Step 2: Start a long-lived container on it**

```bash
docker run -d --name server --network labnet alpine:3.20 sleep 3600
```

- [x] **Step 3: From a second container on the same network, reach the first by NAME**

```bash
docker run --rm --network labnet alpine:3.20 ping -c 2 server
```

Expected: replies from `server` — DNS resolved the name to its IP.

- [x] **Step 4: Prove the name only resolves inside that network**

```bash
docker run --rm alpine:3.20 ping -c 2 server
```

Expected: `ping: bad address 'server'` — this container isn't on `labnet`, so the name doesn't resolve.

**Checkpoint:** name resolution works on `labnet` and fails off it. Clean up:

```bash
docker rm -f server
```

```bash
docker network rm labnet
```

### Task 5 (Weekend): Run Mosquitto, the MQTT broker

**Concept.** MQTT is a lightweight publish/subscribe protocol for devices. A *broker* (Mosquitto) sits in the middle: publishers send to *topics*, subscribers receive from topics they're subscribed to. No direct connection between them.

- [x] **Step 1: Broker config**

Create `mqtt/mosquitto.conf`:

```
listener 1883
allow_anonymous true
persistence true
persistence_location /mosquitto/data/
```

(`persistence true` is what lets the broker remember queued QoS 1/2 messages across a restart — you'll use that in Task 7.)

- [x] **Step 2: Run the broker with the config and a data volume**

```bash
docker run -d --name mosquitto -p 1883:1883 -v "$(pwd)/mqtt/mosquitto.conf:/mosquitto/config/mosquitto.conf" -v mqttdata:/mosquitto/data eclipse-mosquitto:2.0
```

- [x] **Step 3: Confirm it's listening**

```bash
docker logs mosquitto
```

**Checkpoint:** logs contain `mosquitto version 2.0.x running` and `Opening ipv4 listen socket on port 1883`. If it exited, the config path is wrong — check `docker ps -a`.

### Task 6 (Weekend): Python publisher and subscriber

**Concept.** You'll write two small programs using `paho-mqtt`. Note paho-mqtt 2.x requires you to declare a callback API version — that's the `CallbackAPIVersion.VERSION2` argument below; older tutorials omit it and break.

- [x] **Step 1: Python venv + client library**

```bash
py -m venv .venv
```

```bash
.venv/Scripts/python -m pip install "paho-mqtt==2.1.0"
```

- [x] **Step 2: Write the subscriber**

Create `mqtt/sub.py`:

```python
import sys
import paho.mqtt.client as mqtt

QOS = int(sys.argv[1]) if len(sys.argv) > 1 else 0

def on_connect(client, userdata, flags, reason_code, properties):
    print(f"connected rc={reason_code}; subscribing at QoS {QOS}")
    client.subscribe("sensors/temp", qos=QOS)

def on_message(client, userdata, msg):
    print(f"got: {msg.payload.decode()} (qos={msg.qos})")

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="sub-1")
client.on_connect = on_connect
client.on_message = on_message
client.connect("localhost", 1883, 60)
client.loop_forever()
```

- [x] **Step 3: Write the publisher**

Create `mqtt/pub.py`:

```python
import sys
import time
import paho.mqtt.client as mqtt

QOS = int(sys.argv[1]) if len(sys.argv) > 1 else 0

client = mqtt.Client(mqtt.CallbackAPIVersion.VERSION2, client_id="pub-1")
client.connect("localhost", 1883, 60)
client.loop_start()
for i in range(5):
    payload = f"reading {i}"
    info = client.publish("sensors/temp", payload, qos=QOS)
    info.wait_for_publish()
    print(f"sent: {payload} (qos={QOS})")
    time.sleep(1)
client.loop_stop()
client.disconnect()
```

- [x] **Step 4: Run them (two terminals)**

Terminal A (subscriber):

```bash
.venv/Scripts/python mqtt/sub.py 0
```

Terminal B (publisher):

```bash
.venv/Scripts/python mqtt/pub.py 0
```

**Checkpoint:** the subscriber prints `got: reading 0` … `got: reading 4`. Publish/subscribe works end to end. Leave Task 5's broker running for Task 7.

### Task 7 (Weekend): Prove the QoS difference by breaking things

**Concept.** QoS 0 = at most once (fire and forget). QoS 1 = at least once (retried until acked, so duplicates are possible). QoS 2 = exactly once (a four-step handshake). You'll *see* the difference, not just read it. The mechanism: a subscriber with a **persistent session** asks the broker to hold messages for it while it's offline — but the broker only holds QoS 1/2, never QoS 0.

- [x] **Step 1: Write the prediction FIRST**

In `LOG.md`, before running anything, write what you think will happen for each QoS when the subscriber is offline during publishing. Commit that prediction.

- [x] **Step 2: Make the subscriber's session persistent**

In `mqtt/sub.py`, change the client construction to keep its session and re-subscribe with the persistent flag. Replace the `mqtt.Client(...)` line with:

```python
client = mqtt.Client(
    mqtt.CallbackAPIVersion.VERSION2,
    client_id="sub-1",
    clean_session=False,   # broker keeps this client's session + queued msgs
)
```

- [x] **Step 3: The experiment — subscriber offline during publish**

1. Start the subscriber once at QoS 1 so the broker registers its session, then Ctrl-C it:

```bash
.venv/Scripts/python mqtt/sub.py 1
```

2. With the subscriber stopped, publish 5 messages at QoS 1:

```bash
.venv/Scripts/python mqtt/pub.py 1
```

3. Restart the subscriber and watch what arrives:

```bash
.venv/Scripts/python mqtt/sub.py 1
```

Expected: the 5 messages published while it was offline are **delivered on reconnect** — the broker queued them for the persistent session.

- [x] **Step 4: Repeat at QoS 0 — messages vanish**

Redo Step 3 but pass `0` to both scripts. Expected: messages published while the subscriber is offline are **never delivered** — QoS 0 is not queued.

- [x] **Step 5: Kill the broker mid-publish**

Start the subscriber at QoS 1. Start a publisher at QoS 1, and while it's running:

```bash
docker restart mosquitto
```

Watch the publisher — `wait_for_publish()` blocks and the client reconnects and re-delivers unacked messages once the broker is back (that's the "at least once" retry). Note in `LOG.md` whether any message arrived twice.

**Checkpoint:** your `LOG.md` has, side by side, your prediction and what actually happened for QoS 0 vs 1, plus whether the broker restart produced a duplicate. The gap between prediction and result is the week's lesson. Clean up:

```bash
docker rm -f mosquitto && docker volume rm mqttdata
```
